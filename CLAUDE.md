# Starbase: notes for Claude

Community gallery for Datastar Rocket web components. Go 1.27, templ, SQLite (modernc, pure Go), Datastar v1.0.4 + Rocket, vendored in `static/vendor/datastar-rocket.js` as a **patched build**: `patches/rocket/*.patch` on the v1.0.4 tag, built by `go tool task vendor` (`scripts/vendor-rocket.sh`), which also writes its declarations to `internal/tscheck/types` for the playground's type check. Install snippets pin the same build: `SyncCatalog` stores every build it sees under the reserved slug `datastar` (`catalog.DatastarSlug`), served immutably at `/c/datastar@<hash>/datastar-rocket.js` like a component version, and a new catalog snapshot records its build. Drop a patch once its fix is released upstream. Components must keep working on the official release too: they carry their own workarounds (server-wins attribute watchers, their own `attachInternals`, form listeners, window listeners in `setup`).

## Commands
- `go tool task live`: dev server (air, `-tags dev`; live reload rides on the render streams: a stream that reconnects with the boot id of an earlier run gets a reload)
- `go tool task test`: `go vet` + `go test ./...`. `TestCodeEditorLinesAlign` (`internal/app`) drives headless Chrome like `cmd/manifests`: it skips without Chrome, and without a sandbox unless `STARBASE_CHROME_NO_SANDBOX=1`. Run `go tool templ generate` after editing `.templ` (the `_templ.go` files are committed).
- `go tool task new -- <slug> --category <cat>`: scaffold a component
- Browser tests that need what a page can't fake (real pointer and key input, `forced-colors` emulation, the accessibility tree, screenshots) use `probeCDP` (`internal/app/cdp_test.go`): Chrome over `--remote-debugging-pipe`, which the page drives with `POST /__probe/cdp`; `STARBASE_SHOTS=<dir>` saves its screenshots. Like `probeBundle`, it runs on `STARBASE_DATASTAR_BUNDLE`.
- `go tool task ts`: compiles TypeScript components (`components/<slug>/<slug>.ts`, plus helper `.ts` modules and `.d.ts` declarations in the folder; `internal/tsgen` with the embedded compiler, strict, one program for all of them) into the committed `.js` next to each `.ts` (tsc's output, comments kept, relative `./x.ts` imports rewritten to `./x.js`, with a "Generated from" header). Imports stay 'datastar' and the folder's own files: no npm, no `require`. `catalog.Transpile` rewrites relative `.ts` imports the same way for the playground's runner, and the playground's check gets the folder's `.ts`/`.d.ts` (`Catalog.TypeScriptFiles`). Everything downstream (catalog, hashes, `.min`, manifests, previews, self-host) sees only the `.js`; `Component.SourceFile` is the `.ts`, which the playground opens as `component.ts`. `TestComponentsUpToDate` fails on type errors or drift. Edit the `.ts`, never the generated `.js`.
- `go tool task listings`: fills and refreshes Go listings in `components/*/README.md` and `content/*.md` (`internal/listings`): a fence ```` ```go source=<path>#<Name>,<Type.Method> ```` holds those declarations with their doc comments, and the site captions it with a link to the file (`catalog.SourceURL`, from `REPO_URL`). `TestListingsUpToDate` fails on drift, so after editing a listed handler, run the task. Server code in docs is a listing of real code (the demo endpoints, commands), not a hand-written sketch.
- `go tool task manifests`: regenerate all `manifest.json` in headless Chrome (`cmd/manifests`, runs the app in-process); `--check` in CI. Dev pages publish them from the readable modules (`/c/index.js`, and only those: the bundle and `.min` files are shrunk, see Versioned URLs). Chrome keeps its sandbox (submitted code runs there); on machines without one, set `STARBASE_CHROME_NO_SANDBOX=1` (never in CI).

## Performance and SEO
- Responses to GET/HEAD are compressed (brotli/zstd/gzip, `edge.Compress`); render streams (POST) compress themselves (`lith/sse`, set in `app.HubOptions`: zstd at its fastest level with low-memory history where the browser takes it, else brotli) and bypass it. A stream's first write picks the smallest window that holds its largest frame (the gallery's 130 KB: 2^18; the data table's 263 KB: 2^19), at most 2^19 (`ZstdWindow`, `BrotliWindow`; `sse.BudgetOptions.MaxWindow` raises the cap). A page whose frame outgrows every window still gets in, at the smallest tier, and sends larger deltas until it gets a bigger one. Before lith sized windows from frames and flushed brotli within a frame, a gallery frame's delta took 522 B at 2^18 and 174 B at 2^19; not measured again since (`sse.BudgetOptions.MinWindow` 19 would give every stream 2^19, 0.5 MiB more per brotli stream). Memory, not a count, caps the streams: they share a budget of 120 MiB (`app.streamBudget`; at 150 MiB of zstd tabs the server alone reached 317 MiB resident against `MemoryHigh=320M`, and a type check adds about 65 MiB) that books what each holds, its encoder's tier, 32 KiB besides, and the newest frame of each view two or more streams watch (a tab's own view, its whole `#app`, one per tab also on the gallery, keeps none once its stream has it; the Showcase's board region is shared). With `Refuse` the budget turns away a stream without room for a window that holds its first frame (`hub.Serve` waits for that frame, at most a tick, and passes its length as `sse.Options.Frame`, so the headers go out with it), uncompressed ones too: `hub.Serve` answers 503, logged once a minute (`roomWarn`), and the page's retry 'error' asks again (400 ms doubling to 4 s, for ever; `#stream` resets `$_quiet` on Datastar's `retrying` fetch event, so the watchdog leaves the backoff alone). Every stream let in compresses with a window that holds its frame (zstd keeps that tier booked while it has no encoder and moves no lower), and after a refusal the zstd streams above it move down to it at their next write, the 5 s ping, so the tab asking again gets in if that makes room. `TestStreamBudgetCapsTabs` (`internal/web`): 105 tabs of `/components/data-table` with zstd (2^19), 65 with brotli only (28 at q4, 37 at q3, both 2^19), 80 when half are each, 196 of `/about` (2^15). live's `MaxStreams` stays at its default (2000), a backstop. Set `Vary` with `Add`, never `Set`.
- `BenchmarkShowcaseJoins` (`internal/web`) measures the renders and read transactions of 100 tabs joining `/showcase` one after another (200 each, 2026-10-12, i5-13500), and the heap each open stream holds with `app.HubOptions` (1.1 MiB). `BenchmarkBoardPaint` opens 150 tabs (20 on `/showcase`) while one person paints at the paint limit for 10 s: 1 render per tick (the board's view) and 0.03 to 0.15 cores. While a paint touched every page, the same run took 150 renders per tick and 6.7 to 11 cores at GOMAXPROCS 20, 2.9 to 3.8 at GOMAXPROCS 4 (2026-10-13, i5-13500, runs with and without other load on the machine).
- Memory (`internal/app`, for the unit's `MemoryMax=384M`), measured 2026-10-13 with the production binary under load from another process, GOMAXPROCS 4: 105 MiB idle after warm-up (about 50 MiB Go, 27 MiB SQLite outside the Go heap, 28 MiB mapped files), plus 1.1 MiB of heap per open stream on `/showcase` to 1.36 MiB on `/components/data-table` with zstd's low-memory history (`sse.Options.ZstdLowMemory`; 1.7 to 1.95 MiB without it, 1.6 to 2.5 MiB for a brotli stream at 2^18, 0.5 MiB more at today's 2^19). The low-memory history cost no CPU that showed next to the renders (100 `/showcase` tabs while the board was painted: 0.59 cores, 0.67 without it). With the stream budget of 120 MiB full and every tab rendering three times (`TestStreamBudgetCapsTabs`, in process, 2026-10-14), the data table's page peaks at 198 to 224 MiB of heap in use, 228 to 256 MiB of Go runtime (it reaches `app.MemoryLimit` and the GC holds it there) and 219 to 241 MiB resident, so a type check (about 65 MiB) fits under `MemoryHigh=320M`; 196 tabs of `/about` reach 272 to 277 MiB resident, which a type check takes past it, under `MemoryMax`. `main` sets the GC's soft limit to `app.MemoryLimit` (256 MiB) unless `GOMEMLIMIT` is set: without it the heap grows to twice what is live, and 150 streams took 449 to 494 MiB while the board was painted; with it, 247 to 263 MiB at GOMAXPROCS 4 to 16. `MemoryHigh=320M` throttles only past that plan.
- Pages load every component as **one bundle** (`/c/bundle.js`, esbuild, `catalog.Bundle`; lazy `import()`s stay lazy) while its brotli size fits `web.bundleBudget` (100 kB); over budget they fall back to the autoloader, with a warning at startup. `?load=auto` / `?load=bundle` override it for measuring. Measured on production: the bundle wins any visit that includes the homepage and costs a single-page lander ~265 ms on slow 4G at 66 kB. The bundle also removes `sb-cloak`, like the autoloader.
- Static and generated assets (component modules and `.min` files, the autoloader, `/c/bundle.js`, CSS bundles, art, text files under `/static/`) go out **precompressed** (`edge.ServePrecompressed`: brotli -11 and gzip -9, memoized by content, with an ETag, warmed in the background at startup); the middleware skips anything with `Content-Encoding` set. Only HTML documents are compressed per request. The catalog's size tables measure through the same cache (`edge.Precompress`), so a size shown is the bytes sent (`TestSizesAreBytesServed`).
- A render keeps what depends only on the binary in `renderCache` (`web/rendercache.go`, about 2 MB with every component): the install tabs per component (once every integrity they pin is stored, since stored integrities never change), a component page's Playground, Size and API sections, the Themes page's highlighted CSS, the content pages' Markdown, the playground's import list and the site's JSON-LD. chroma took 80 to 95% of a component page's render before. Nothing there may depend on the session, a preference, the tab or a nonce; `TestRenderCacheMatchesFresh` renders every page with an empty cache and from it, and `BenchmarkRenderFrame`/`BenchmarkRenderGET` measure a page (`-memprofile`, `-cpuprofile`), `BenchmarkStreamFrame` a stream's frame with its patch event. A stream's frame renders into a pooled buffer (`frameBufs`), since `sse.PatchElements` copies it.
- Hashed static files are `immutable`. `robots.txt`, `sitemap.xml` (pages + active components), `/og.png`, `/apple-touch-icon.png` and `/favicon.ico` (PNG, rendered from the pixel art: `pixelart/png.go`) are in `web/seo.go`. Every page has a canonical URL, Open Graph/Twitter tags and JSON-LD (`WebSite` with a search action; component pages add `SoftwareSourceCode` via `view.Schema`).

## Deploy
- `deploy/`: host files (systemd unit, env, the Caddy site `starbase.caddy`, installed by hand into `/etc/caddy/sites/`), `observability/` (the scrape target, the blackbox probe and the Alloy file for the host's drop-in folders), `starbase-metrics.socket`, `starbase-deploy` (root; verifies, restarts, checks `/healthz`, rolls back) and `setup-host.sh` (installs the `observability/` drop-ins, reloading Alloy and rolling back a file it refuses; with a key, also the restricted `starbase-deploy` user with a forced-command key). `.github/workflows/deploy.yml` runs after CI on `main`, gated by the repository variable `DEPLOY_HOST`.
- Metrics (`cmd/starbase/metrics.go`): lith/prom's writer, live and stream budget numbers under `starbase_`, with `go_*` and `process_*`, on a loopback listener of their own (`METRICS_ADDR`), never the public one. On the host `starbase-metrics.socket` holds 127.0.0.1:8198 and passes it in, since the service's `IPAddressDeny=localhost` would drop Prometheus' connections too; the socket unit's own filter applies to that socket alone. The port is in the socket unit, `starbase.env.example` and `observability/starbase.metrics.yml` (`TestMetricsPort`); `TestDashboard` checks the names against lith's dashboard and alert rules.

## Architecture rules (CQRS on lith)
Starbase runs on lith (`github.com/zweiundeins/lith` v0.4.1, and `lith/prom` for the metrics): `sqlite`, `writer`, `live` and `sse`, and `edge` for sessions, the security headers, compression, precompressed assets and the client key. The lith skill (`/develop/lith/skills/lith/SKILL.md`, with `references/`) holds the rules every lith project keeps (one writer, commands that touch topics, views rendered once per tick, the outcome on the stream, state in SQLite, bounded streams) and the review checklist. Starbase's own:
- Commands (`internal/commands`) are structs with `Apply(*writer.Tx)` and an optional `Validate()`. They touch the topics of `commands/topics.go`: `TabTopic` for tab state, `SessionTopic` for session preferences and sign-in, `TopicAll` for what every page shows (stars, the catalog), `TopicBoard` for the pixel board, which only the board's view shows; seeds and prunes touch none. `TestTopics` lists each command's topics. Handlers queue through `s.send` (the writer's `Send`: 204, or 400 for `writer.ErrInvalid`); sign-in and sign-out wait with `Do`.
- `internal/db` opens the database with `sqlite.Open`: synchronous NORMAL, the writer checkpoints (no Litestream), and a read pool of twice the CPUs, since every render worker holds a connection for good. A document reads through `queries.Queries.View`, a stream's render through `queries.Read` on its worker's transaction.
- Pages are `pageFunc`s in `internal/web` registered with `s.page(mux, pattern, fn, regions...)`: the GET document, and the POST render stream, `hub.Serve` with the tab's view (key `tab:<tabid>`, topics `sid:<sid>`, `tab:<tabid>` and `all`; its frame is the whole `#app`) and the views of the page's regions (`web/region.go`): parts of the page that all its viewers share, each a view of its own (the Showcase's board, see Pixel board). In a document the page renders a region in place (`rc.region`); the tab's view leaves a hole there, which the stream's `WriteTick` fills with the region's newest frame, so the morph of `#app` leaves the region alone. A region never sits in `data-ignore-morph`: Datastar would skip its own frames too. A page must be a pure function of `renderCtx`. In a stream it renders on a render worker, and a render that waits holds up the whole tick: nothing in a page waits on the network (`warmPreview` fetches a pull request preview in the handler first). A page that is gone renders the not-found page in its stream as in its document.
- A page opens its stream from `<div id="stream">` (`ui.StreamID`, `streamInit`), outside `#app` and never from the body, with `retry: 'error'`, and the stream's `Spec.Reconnect` names that element. When the hub stops (a deploy), each stream ends with `sse.Reconnect`, which replaces the element by a copy whose data-init opens the stream on the next process, and `'error'` retries the 502s and 503s in between; a stream the server ends otherwise stays closed. `/demo/telemetry` does the same for `#telemetry` (`ui.TelemetryID`, one per page: Mission Control and the gauge, meter and sparkline docs) and answers 503 while the server stops. `TestStreamsReconnectAfterDeploy` (`internal/app`, Chrome) restarts the app under an open Showcase. `'error'` also repeats every 4xx, so a stream request the server refuses for good (malformed, cross-site, or for a page that doesn't exist) gets 204 (`refuseStream`); `streamRequest` knows a page's stream by its `Accept: text/event-stream`.
- A connection dropped without FIN or RST leaves a stream silent, not closed. The hub's heartbeat patches `$_ping` (`ui.PingSignal`, `live.Options.HeartbeatSignal`) every `config.StreamHeartbeat` (5 s), frames or not, and a watchdog beside `#stream` (`watchdogTick`, `data-on-interval` at the same pace) re-creates `#stream` after 3 to 4 heartbeats without a new number (15 to 20 s), as `sse.Reconnect` does; the new `@post` to the same URL aborts the silent one. lith's first ping comes a heartbeat after a stream opens, so the stream's first write also patches `$_quiet` to 0 (`resetWatchdog`, `web/region.go`): after an outage the count could be one tick short of firing and tore the new stream down (`TestWatchdogKeepsAReconnectAfterAnOutage`). Hidden tabs reset it (their stream is closed on purpose). Its counting runs in the interval alone: with a `data-effect="$_ping; $_quiet = 0"` beside it, `$_quiet` stayed 0 and the watchdog never fired. `TestWatchdogReopensASilentStream` (`internal/app`, Chrome) silences a stream mid-page.
- Streams outside the hub and compressed answers use lith's `sse` too (`sse.Open`, `Write`, `CloseWith`), which ends the compressed stream: datastar-go's generator never closes its encoder, so its brotli and gzip answers end without their last block. `/demo/telemetry` goes out uncompressed (an event is 130 bytes, an encoder 430 KiB or more per open page), `/demo/data/list` and `demoAnswer` (`/demo/data/rows`, `/children`, `/search`) compressed (`TestDemoListEndsItsStream`, `TestDemoDataEndpoints`). datastar-go stays for small one-shot answers (`MarshalAndPatchSignals`) and `ReadSignals`; `edge.Compress` skips `text/event-stream`, so those go out uncompressed, and anything larger than a few KB belongs on `sse`.
- A session is a cookie (`edge.Sessions`): 256-bit ids, and the 160-bit ids starbase made before stay valid (`Accept: legacySessionID`), so no one is signed out. Sign-in renews the id.
- Preferences that should outlive a page (they carry across navigations and browser tabs) are session preferences (`session_prefs`, keyed by sid, set by commands, read into `renderCtx.prefs`, so the first GET renders them); `tab_state` lives for one loaded page (`tabid` is new on every document). A new preference is one field in `model.SessionPrefs` plus its command (`commands/prefs.go`), like `SetInstallTab`. Today: the install tab, the Themes preview (`SetPreviewTheme`, `SetPreviewStyle`) and the gallery's default sort (`SetGallerySort`, `POST /cmd/sort`): a page without stored state takes the sort from its URL when it names one, else the session's (`BrowseFromQuery(q, prefs.DefaultSort())`), and `Browse.QueryFor` drops the sort from URLs only when it and the default are both "popular". Search and category (`/cmd/browse`) never change the default.
- Exception: the site theme is a browser preference, kept by `sb-theme-switch` in the `sb-theme` cookie. The layout renders it (`Shell.Theme`, `siteTheme`) on `<html data-sb-theme>`, so there is no flash. "auto" means no attribute: `:root` is deep-space, and `/theme/auto.css` (generated from the daylight block in `css/themes/showcase.css`) applies daylight on light systems.

## Frontend rules
- 8-bit details are opt-out: pixel-corner clip-paths scale with `--sb-notch` (1 or 0; at 0 use a border radius), frames with `--sb-frame-step`, display text uses `--sb-font-display` and, where it is in capitals, `text-transform: var(--sb-display-case, uppercase)`. Every other pixel detail follows `--sb-notch` too, with the value itself driven by it (a source scan flags literal `steps()` and fixed-px polygons): a stepped polygon's vertices are `calc(smooth + (pixel - smooth) * var(--_notch))`, a stepped timing is `steps(calc(N + (1000 - N) * (1 - var(--_notch))))`, and a low-resolution canvas reads the notch at paint time (sb-gauge, sb-sparkline: a transitioned `stroke-width` carries it) and draws at device resolution at 0. Pixel art by design (starfield, nebula, voxel, pixel-board) stays. `[data-sb-style="smooth"]` (theme.css) sets all four; the Themes page switch is the session preference `SessionPrefs.PreviewSmooth`.
- CSS: `@layer reset, tokens, theme, base, layout, components, utilities`. Pages load one minified bundle (`/bundle/site.css`, built at startup from `siteStylesheets` in `web/assets.go`, font URLs rewritten to hashed names); a new stylesheet must be added there. The playground runner gets `/bundle/runner.css`.
- Fonts: component text sets no `font-family` of its own, so it inherits the page's. Where a component uses a font token, text falls back to the page's font, not to a named font: `font-family: var(--sb-font-display, inherit)`, or, for a canvas that needs a font name, the element's computed `font-family` when the token is unset (`sb-echarts` `font()`). Only code (editor, console) falls back to monospace. On Starbase the tokens are set, so nothing changes there.
- Overlays (popover, select, dropdown, date picker, column picker, modal, drawer, tooltip, toast, theme-switch menu) draw their shadow from `--sb-shadow-overlay` through a `--_shadow` local whose fallback is the component's own shadow. The token is one shadow without spread, or `none`: components that clip to notched corners read it in `filter: drop-shadow()`, which takes no spread. A new overlay does the same.
- Syntax colours are semantic tokens (`--sb-code-keyword|function|tag|string|number`), with light values in the daylight block; don't use palette primitives (`--sb-violet-3`…) for anything that must work on light themes. Use semantic `--sb-*` tokens (theme.css) in components, not primitives. Prefer container queries over media queries.
- **Wire components declaratively:** events use `data-on:*` with local `action()`s (`@name()`), state is `$$` signals with `data-bind`/`data-show`/`data-class`/`data-attr`/`data-text`/`data-effect`, lists use `<template data-for>`, and elements come from `data-ref:x` → `onFirstRender({ refs })` (refs are not `$$` signals). `data-bind:x` in rendered markup binds the local `$$x`. Plain `addEventListener` is only for things without an attribute form (`matchMedia`, Intersection/ResizeObserver), and for window/document listeners: `data-on:*__window` inside a shadow template outlives the element and throws `UndefinedAction` after removal, so add those in `setup` and remove them in `cleanup`.
- Rocket components (`components/<slug>/`): shadow DOM (default mode), `adoptStyles(host, css)`, `--_x: var(--sb-x, fallback)` locals, interaction state in `$$` signals (never reflected to attributes, because server morphs reset attributes), `emit()` for events, `.docs()` on every prop.
- **Keyed elements with Rocket components inside:** Datastar v1.0.4's morph is not re-entrant, and Rocket renders synchronously in `connectedCallback`, so `id`s on repeated or reordered elements that contain Rocket components crash it (`Maximum call stack` / `moveBefore` HierarchyRequestError). The patched build fixes it (`patches/rocket/0008`, upstream #1209, fixed for their next release), so Starbase's own pages may key them: the gallery cards have ids, and a sort moves them with their live previews. Component code and docs examples must not rely on it, since the official release still crashes. Repro and fuzz results: `docs/repro/rocket-morph-reentrancy/`.
- `data-bind` on a custom element only writes to an existing signal. Declare it with `data-signals` first, and use `__prop.value` / `__prop.checked`: Datastar binds before Rocket upgrades the element, and otherwise falls back to the attribute, which morphs strip.
- Component host getters and setters over `$$` (`overrideProp`) must use `startPeeking()`/`stopPeeking()`, or `data-bind`'s effect subscribes to the internal signal and writes stale values back.
- The server can set every value: a form component's `value`/`checked` attribute **wins when the server sends a new one** (`observeProps` on that prop). Re-sent identical markup changes nothing, so user edits survive morphs. A *removed* attribute is ignored (`host.hasAttribute` check): morphs also strip attributes that were only reflected, e.g. by Rocket's upgrade replay of a `data-bind` write made before the element was defined. To clear, the server sends `value=""` / `checked="false"`. Property writes go through `overrideProp` into `$$` and never reflect. Rocket replays pre-upgrade property writes into `props` itself: no manual adoption needed.
- Command contract for value components (input, slider, toggle, code-editor, tabs; rating, select, tree; checkbox, checkbox-group, date-picker, and sb-data-table's `selected`): a `name` prop; `sb-change {name, value}` on commit; `confirm` sets `:state(pending)` (ElementInternals custom state, `internalsOf(host)` caches the internals since `setup` reruns on re-attach) while `$$` differs from the server's attribute; `host.revert()` restores the server's value. Pages: `data-on:datastar-fetch="evt.detail.el === el && evt.detail.type === 'error' && el.revert()"` (fetch events reach every listener). Demo: `SetFlight` / `POST /cmd/flight` / `ui.FlightDemo` on the Showcase.
- A server that normalises a value back to what it already held sends identical markup, so the component can't tell "answered" from "not yet": `sb-input` takes an optional `rev` (a revision the server bumps with every applied command, e.g. `CallsignRev` on the Showcase) and treats a new `rev` as the server's word. Other value components don't have it yet.
- Every component: `:host([hidden]) { display: none }` wherever `:host` sets `display`; styles for `disabled` (and other booleans) come from the decoded prop (`:state(disabled)` or the inner control's `:disabled`), never `:host([disabled])`, which also matches `disabled="false"`; a `@media (forced-colors: active)` block keeps focus rings (a transparent outline) and glyphs (`CanvasText`) visible; a token's hex fallback is the same in every component (`TestTokenFallbacksAgree`).
- Form-like components (input, select, radio-group, toggle, slider, range, rating, code-editor, checkbox, checkbox-group, date-picker) join the `<form>` they sit in until Rocket can declare form association: `formdata` and `reset` listeners on `host.getRootNode()` that act only when `evt.target === form` (a reset not when `defaultPrevented`, so a cancel from any listener on the form is honoured), appending what the native counterpart would submit, nothing without a `name` or while `disabled`; a reset restores the server's value without change events. `TestFormParticipation` (`internal/app`, Chrome) checks all eleven. Validity, `<fieldset disabled>`, `<label for>` and `form="id"` need real form association (upstream).
- No optimistic updates: never show a server result (counts, lists, derived values, success messages) before the server renders it; the user's own input stays, marked `:state(pending)` (or faded items for operations), and `revert()` on rejection.
- Several values: parts of one decision are one structured `value` (JSON attribute, one `sb-change`, one command; e.g. `sb-range` `{start, end}`); view state (`expanded`; sb-data-table's `hidden-columns` and `widths`, `{key: px}` with `sb-column-widths`, both server-wins like a value) is a separate prop and event, never pending, and `revert()` leaves it; server data (`results`, `options`) only flows in; operations (paint, move) emit `sb-<verb>` with per-item pending until the echo.
- Server data for components are props the server can morph (e.g. `sb-select` `results`, `sb-tree` `loaded`/`expanded`), not only signals.
- Rocket/Datastar gotchas (learned the hard way):
  - `observeProps` only fires when the *decoded* value changes (`#setProp` returns early on `Object.is`). So `checked="false"` written onto an element that never had the attribute is silent, and a local edit would survive a server clear. Every value component therefore watches its value attribute itself (`new MutationObserver(…).observe(host, { attributeFilter: ['value'] })`, the pattern in `sb-details`) and applies server-wins there; `TestServerWinsContract` (`internal/app`, Chrome) checks all of them (a JSON value like `sb-range`'s may use observeProps, since its codec never decodes to the default).
  - Never call a component `action()` from `data-effect`: Datastar's effect flush can run it after the element was cleaned up (`UndefinedAction`, and the replacement element renders empty). Use `effect()` in `setup` instead.
  - Host ARIA that must survive a morph goes through `ElementInternals` properties (`internals.ariaBusy`, `internals.role`), like `:state()`; an attribute set from an effect is stripped by the next morph and the effect never re-runs.
  - Assigning an object to a signal *merges* into it (keys are never removed, except by a `null`, which deletes that signal and leaves every effect that read it stale: use `false` or `''`), and reading a missing key creates it. Keep maps and sets that change in plain closure variables, and expose only what the template renders (e.g. `$$.rows`).
  - `observeProps` callbacks run inside the effect of whoever set the attribute (e.g. `data-attr:x`): wrap them in `peek()`, or their signal reads subscribe that effect (infinite loops). The official release does the same; a callback that writes a new array loops for good (`TestBoundPropsSettle` binds the components that write signals from one).
  - With `renderOnPropChange` (the default) every prop change re-renders the whole template, dropping keyboard focus. Components with focus or live state: `renderOnPropChange: false`, and drive the markup through signals.
  - Style rows by a prefix or class (`[role^="menuitem"]`), never an exact `[role="menuitem"]`, in a component that can change a row's role: the value-bearing variant (`menuitemradio`) silently loses every rule, and a presence-only test won't see it.
  - Lists that hold focus (tree, menu, radio group): a morph parks a row before removing it, so `focusout` arrives with the row still connected and `relatedTarget === null`, exactly like a click on the page. Decide it a microtask (or a frame) later: row gone → the server dropped it, keep the flag; row still there → the user left, clear it (treating every null as "not leaving" made the group steal the focus back on the next server update). Restore focus only when `document.activeElement` is the body or the host, and move to the *neighbour* of a dropped row (old index clamped), not the first. Documented for contributors in contribute.md.
  - A morph that reaches a Rocket host (`data-scope-children`) re-runs every `data-init` inside it, on both builds: put a `data-init` (e.g. one that moves the focus) only in the markup that should run it.
  - `<template data-for>` can re-evaluate a removed row once with the loop variable undefined when the list shrinks: use `r?.x` in row expressions.
  - Never call a `data-for` row variable `i`: without an explicit index (`r, k in …`) Rocket names the index `i`, which overwrites the row with its number (every `i?.x` reads undefined).
  - Rocket moves `data-signals:x` on a shadow component's light-DOM children into the component's own scope (`_rocket.<tag>.<id>.x`) whenever it gets to them before Datastar does (usual with cached modules), while `$x` reads there stay global: declare page signals on an element outside the component (the playground's `$_size` sits on `.code-page__island`). An upstream candidate.
  - Chrome sends no `selectionchange` to a textarea inside a shadow root: follow the caret with `input`, `keyup` and `pointerup` (sb-code-editor's problem line).
  - A Rocket component in another component's template whose children bind the outer's `$$` (sb-data-table's rows inside its sb-virtual-scroll): when the inner tag is already defined, `importNode` upgrades it on the spot and it claims those children's `$$` for its own scope, so they render empty (every table created after page load did). Render such children outside it (a hidden element) and move them in during `onFirstRender`, as sb-data-table does. An upstream candidate.
  - Server data for a component: it emits an event (`sb-load`, `sb-search`), the page answers with `@get`, the server patches a signal (or morphs the prop), `data-attr` hands it back (see `sb-tree`'s JSON form, and the generic `/demo/data/…` endpoints for demos). Or the server renders markup inside the element, which works before JavaScript: the component reads it as data (a MutationObserver), draws its own copy in the shadow root (the source isn't slotted), and keeps view state like open branches in its closure, so morphs of the source don't reset it (`sb-toc`, `sb-tree`'s lists, whose lazy branches get a `<ul>` patched into their `<li>`).
- sb-data-table's header and each row are grids of their own on one `--cols`: `ch` and `em` in a column width resolve in each row's font, so header type goes on `.th` (`::part(column)`), never on the header row (`TestDataTableColumns`). A clipped cell peeks (`data-peek`, set from JS on hover and focus only when `scrollWidth > clientWidth`) inside `.row { overflow-x: clip }`, so sb-virtual-scroll's scroll size never changes.
- Hosts whose attributes are driven by signals (`data-attr:x=...`) need `data-preserve-attr="x ..."`: the morph resets every attribute to the server markup.
- Layers (sb-modal, sb-drawer, sb-popover, sb-dropdown, sb-select, sb-date-picker's calendar) close innermost first on Escape, in any nesting. A modal `<dialog>` relies on its `cancel`: the browser sends the close request to the top layer, and an inner control that uses the key calls `preventDefault` on the keydown, which stops it. A layer that handles Escape itself never acts on a `defaultPrevented` key, nor on one from inside another open layer nested in it (`:popover-open` or `dialog[open]` on `composedPath()` before its own element; see sb-drawer's non-modal mode). `popover="auto"` gets all this from the browser (sb-date-picker); sb-select stays `manual`, since typing in its field must not dismiss the list.
- Pixel art (`internal/pixelart`) is generated SVG. Theme-aware colours are `var(--sb-art-*, #fallback)` (set per theme in `css/themes/showcase.css`; Deep Space uses the fallbacks), which only apply where the SVG is inlined with `ui.Art` (logo, hero). As `<img>`/favicon the fallbacks show. Its CSS is scoped under `.px-art`.
- `tab_state` is for server-owned UI state of one page (the gallery's search and category, the playground share); choices that should last (install tab, Themes preview theme and style, the gallery's default sort) are session preferences. High-frequency, ephemeral demo state (sliders, playgrounds) stays in local `_`-prefixed signals.
- `unlisted: true` in a component's front matter keeps it out of the gallery, the search index, the sitemap and the site stats, while it stays served, versioned and documented at `/components/<slug>` (migration 007 adds `components.listed`). It is for components the site itself runs on: `sb-code-playground` powers `/playground`.
- Component pages render an auto Playground from the manifest (`internal/catalog/playground.go`, `ui.Playground`). It is a `data-ignore-morph` island driven by local `$_pg` signals, tuned by `playground:` front matter.
- `GET /demo/telemetry` (`internal/web/demo.go`) is a stateless query stream of `$_tm` signal patches for live demos.
- Demo data for components' docs comes from the example dataset (`internal/demo`, seeded by `SeedDemo`): use the generic `GET /demo/data/children` and `/demo/data/search` (`internal/web/demo_data.go`, `&into=` names the signal, `&delay=` for loading states) instead of adding component-specific endpoints. Long lists use the star catalog (`demo.StarAt(i)`, a million stars computed from the index): `GET /demo/data/list` patches an sb-virtual-scroll host with a window of it, and `GET /demo/data/rows` answers sb-data-table with sorted windows of its first 100,000, stored in `demo_stars` by `SeedStars` so SQLite can sort them.
- Canvas components: `renderOnPropChange: false`, repaint on `observeProps`, read theme tokens at paint time (via a 1×1 canvas probe), pause offscreen (IntersectionObserver) and honour `prefers-reduced-motion`.
- The CSP (`Server.csp`, which `edge.SecurityHeaders` asks for each request) uses a nonce (import map) plus `'unsafe-eval'` (Datastar). No inline `<script>` without `s.Nonce`. `script-src` allows only `<origin>/static/` and `<origin>/c/`, not `'self'`: new script locations must be added there.
- Rate limits (`limiter`, per session and per `edge.ClientKey`: from a loopback or Unix-socket peer, the proxy, it takes the last `X-Forwarded-For` address, the one Caddy appends after whatever the client sent, and `X-Real-IP` only without `X-Forwarded-For`; from any other peer, the peer's address): painting, snippet saves. A client key (an IPv4 address, an IPv6 /64) holds at most `maxStreamsPerClient` (24) render streams (`web/streamcap.go`), so no one takes the whole budget. People share an IPv4 address behind carrier-grade NAT, in offices and on conference Wi-Fi, and each needs a stream per visible window, so a crowd behind one address can still reach the cap. Past it a stream gets 429, which retry 'error' repeats, and refusals, like the budget's 503s, are logged once a minute (a load test from one address must send its own `X-Forwarded-For` per client, from loopback). Snippet storage is capped (`MaxSnippetStore`, tracked in `snippet_stats`).

## Versioned URLs
- Minified modules (`catalog/min.go`, esbuild): every module file `x.js` has a `x.min.js` sibling whose relative imports point at the `.min` files: the module-file option of the install snippets loads them, and the bundles' lazy imports point at them. The readable file stays the default URL for docs, the playground editor and "view source". Before minifying, `catalog/shrink.go` takes out what esbuild can't (non-vendored files only): `.docs({…})` calls and the rocket() `manifest: {…}` property (manifest.json is published from the readable modules), and comments and needless whitespace in `/* css */` and `html`/`svg` templates (–18% on modules, –16% on the bundle). A module may use the `manifest:` key only for rocket()'s (a test enforces it); `TestShrunkModulesKeepProps` (`internal/app`, Chrome) checks the bundle still defines every prop of every manifest. `.min` bytes depend on the esbuild version and on shrinking, so they are frozen per version, and a change to either must bump `minFormat` (`catalog.go`, part of every component's hash): `SyncCatalog` stores them in `component_files` (INSERT OR IGNORE) and `serveVersioned` always serves `.min` from there (in memory only before the first sync). Install snippets are built in `Server.install` (`web/views.go`, rendered by `ui.Installation` as `sb-tabs`: Autoloader, This component + its `Catalog.Deps`, Pinned snapshot, Self-host); they pin `.min` with that frozen integrity (`Reader.FileIntegrity`). The chosen tab is the session preference `SessionPrefs.InstallTab` (`POST /cmd/install-tab`, stored by key, not index).
- One-file bundles (`catalog/onefile.go`, `Catalog.BundleOf`): every component also ships as `<slug>.bundle.min.js`, its main module with every static import inlined, shrunk and minified like the `.min` files. `'datastar'` stays external, a dynamic `import()` stays lazy as `./<file>.min.js` next to the bundle (`ComponentBundle.Lazy`: what a page may load after it), and the components it renders are not inlined (their own bundles, `Catalog.Deps`). It is one of `MinFiles`, so it is stored, frozen and served like them (`/c/<slug>@<hash>/<slug>.bundle.min.js`, the snapshot's `importmap.json`). The autoloader's map (`catalog.AutoloaderJS`) and the playground's deps (`assets.ComponentScript`) point at bundles; `requires` loads the bundles of the components one renders. A snapshot's autoloader is frozen under the catalog hash, so `snapshotFormat` (`catalog.go`) is part of that hash: the move to bundles gave the catalog a new snapshot, and older snapshots keep loading module files (`TestSnapshotsKeepTheirMaps`). The Pinned tab's import map pins the bundles and their lazy files. Pages load `/c/bundle.js` within budget, else the autoloader, so nothing on the site loads a module graph but `/c/index.js` (dev, the manifest publisher). `TestAutoloaderLoadsBundles` (Chrome) opens the gallery with `?load=auto`. Its banner names the tag and `<slug>@<hash>`, nothing that depends on the build, so a version's bundle has the same bytes wherever it is built; a change to the banner or to how the bundle is made bumps `minFormat`. The "This component" and "Self-host" tabs offer it first and the module files second; `go run ./cmd/dist -out <dir> [slug ...]` (`go tool task dist`) writes `<slug>.js`, the components it renders and its lazy files from a checkout. Load refuses component files named `<slug>.bundle.js` or `<slug>.bundle.min.js`. Tests: `TestComponentBundles` (catalog), `TestComponentBundleURL` (web), `TestComponentBundlesDefineEveryTag` and `TestKanbanBoardBundle` (`internal/app`, Chrome: a page that loads only bundles).
- Download sizes: `catalog.Load` computes `Component.Sizes`, each file compressed on its own at gzip -9 / brotli -11. The download size, `Sizes.Total` (gallery cards, a component page's meta row and the head of its Size section), is what a page loads with bundles: its bundle (`Sizes.Bundle`) and those of the components it renders (`Sizes.Bundles`; `Catalog.Deps` over `Catalog.Uses`, which the autoloader's `requires` also uses). A file a bundle loads on first use (`Sizes.Lazy`, `UsesLazy`: Prism, ECharts' library) counts in `Total`, since the component loads it as soon as it highlights code or draws a chart, and shows as such: "of which … loaded on first use" (`Sizes.LazyMin`) in the tooltip, its own rows in the Size section. The module files are the secondary view, in a `<details>` "As module files" under the bundles, counted the same way (`Files` over `Catalog.Loaded`: the main module and what it imports, a first-use one marked; a module only the examples use, like autoloader's `demo-badge.js`, is served but not counted; `Own`, `Uses`, `ModulesTotal`, `ModuleFiles`, which the This component tab's count uses too). `Size.Min` is the minified file under brotli; a bundle is minified, so its Min is its Brotli.
- `internal/web/versions.go`: `/c/<slug>@<hash>/<file>` (a component version: current from the binary, older from `component_files`), `/c/@<catalog hash>/autoloader.js` and `/importmap.json` (SRI map). All immutable, `ACAO *`. `SyncCatalog` stores every version and catalog snapshot it sees (migration 005), so pinned URLs outlive deploys.
- Each distinct body is stored once (`file_bodies`, keyed by its integrity, the SHA-384 SRI; migration 010): a `component_files` row (slug, hash, path, integrity) refers to it, so versions share the bytes of the files that didn't change (production stored ECharts' vendored file nine times). `storeFile` (`commands/catalog.go`) inserts the row first, INSERT OR IGNORE so the first bytes stay, and the body only for a new row; the foreign key is deferred to the commit. Bodies are read only by `Reader.ComponentFile` (a join); integrity reads stay on `component_files`. Its `body` column stays, always NULL, so a binary from before 010 still starts after a rollback (it serves the current version from memory, older ones 404); a later migration can drop it. Withdrawing a version: delete its `component_files` rows, then `DELETE FROM file_bodies WHERE integrity NOT IN (SELECT integrity FROM component_files)`. 010 frees the old table's pages, so it ends with the line `-- then: VACUUM`: `db.migrateTo` (lith's `sqlite.Migrate`, run as `Options.Migrate`) vacuums once after committing it (VACUUM can't run in a migration's transaction), only on a database that existed before, and truncates the WAL. On a 39 MB stand-in for production that took 0.25 s and 84 MB peak RSS, and the file went to 22 MB.
- The site uses versioned module URLs too (`assets.ComponentScript`, `catalog.AutoloaderJS`); the old `/c/<slug>/<file>` route stays for compatibility.

## Code playground
- `/playground` page (`internal/web/playground.go`, `ui.CodePlaygroundPage`): sources `?s=<snippet>`, `?component=<slug>` (JS + `Component.Examples`), or a starter. The editor area is a `data-ignore-morph` island; the share strip around it is stream-rendered from `tab_state.PlaygroundShare`.
- `sb-code-editor` highlights with Prism, vendored as an ES module in `components/code-editor/vendor/prism.js` (js-templates plugin, plus `/* css */` templates and `data-*` values as JS). Rebuild it with `go tool task vendor-prism`. Components may import `'datastar'` or files in their own folder; `/c/<slug>/**.js` is served.
- `/playground/run` is the sandbox runner (own CSP, opaque origin via `sandbox="allow-scripts allow-modals"`, a fresh iframe per run). It adds a loop guard to the user's code (a `while`/`for(;;)` condition that runs a single task for over a second throws), since Chrome runs every sandboxed frame of a site in one process and an endless loop would freeze every playground on the page; the component also has a watchdog for runs that never answer. The protocol is documented in `components/code-playground/README.md`. Public assets send `Access-Control-Allow-Origin: *` for it.
- Rocket gotcha: before Datastar is ready, a later `rocket()` call for the same tag replaces the queued one, so the runner imports the edited code first and the parent drops deps whose tags the code defines.
- The size line in the playground's top bar (`ui.PlaygroundSize`, in `sb-code-playground`'s `bar` slot) is a query, not a command: `POST /playground/size` (`web/playground_size.go`, rate-limited, memoized by content) measures `component.js` as its component's bundle with `Catalog.Measure` (bundled with the files of the component's folder, with the bundle's esbuild settings and banner, so unedited code measures exactly its `Sizes.Bundle`, and its total adds what it loads on first use like `Sizes.Total`; 10 to 40 ms, uncached `edge.BrotliLen`) and patches `$_size` with preformatted texts; a parse error patches only `stale`, so the last numbers stay. The first numbers are rendered with the page. It hides detail with container queries on `.code-page__island` (`container: playground`).
- TypeScript: `sb-code-playground`'s `typescript` switch renames `component.js` to `component.ts`; the runner sends it to `POST /playground/transpile` (`catalog.Transpile`, esbuild, with a line map from the source map so errors point at the lines written). The runner is an opaque origin, so that endpoint is the one POST the CSRF check lets through (a pure function, rate-limited per IP, `ACAO *`). Size and check take the module's `name`. TypeScript snippets can't be submitted yet (the catalog takes `.js`).
- Type check: `component.ts`, and JavaScript that contains `// @ts-check`, is checked on every run (with Auto, shortly after each edit; not on `sb-change`, whose debounced request could carry older code and cancel a newer one) by `POST /playground/check` (`web/playground_check.go`, rate-limited, memoized by content) with `internal/tscheck`, together with the module files of the component it came from; the answer is `$_diag`, a JSON string (an object patch would merge) that the playground hands per file to `sb-code-editor`'s `diagnostics`. The compiler is TypeScript's native port (a Go binary, Apache-2.0) run as a subprocess: `tscheck.Version` pins it with each platform's npm integrity (Dependabot doesn't see it), `go run ./cmd/fetchtsc [-os -arch]` puts the target's tarball in `internal/tscheck/dist` (gitignored), and the binary embeds it and unpacks it next to the database. Every build path runs fetchtsc first (Taskfile `live`/`build`/`test`, CI, deploy, release, Dockerfile); without it the check is off and its tests skip. Its guard: a `--listFilesOnly` pass must list nothing outside the temp folder, the lib files and the declarations, else nothing of the check is shown; one check at a time, RLIMIT_DATA 192 MB (not lower: the Go runtime reserves more than 96 MB at start), oom_score_adj 1000 so a cgroup at its MemoryMax kills the check, not the server, `GOMEMLIMIT`, a 10 s timeout.
- Snippets: `SaveSnippet` (≤ 64 KB, immutable, `snippets` table). `GET /playground/snippet/{id}` is public JSON. The submission bot imports playground links only from `STARBASE_URL`.

## Pixel board
- `sb-pixel-board` takes `cells` from the server (not preserved: every morph brings the latest). The board section on `/showcase` is **not** an ignore-morph island; Mission Control is.
- `PaintPixels` / `SeedBoard` in `internal/commands/board.go`; the encoded board is cached per version in `web.boardState`; `/cmd/paint` has an in-memory token bucket (20 px/s, burst 60).
- Paint posts use `requestCancellation: 'disabled'`: Datastar cancels in-flight requests to the same URL by default, which would drop pixels mid-stroke.
- The board (`ui.Board`: who is watching, the pixels painted, the cells) is a region (`newBoardRegion` in `web/board.go`): a view with key and topic `board` that every Showcase stream watches and no other page does. `PaintPixels` touches only `board`, so a paint renders that view once for all viewers and no tab's view (`TestPaintRendersTheBoardAlone`, `BenchmarkBoardPaint`). The view has `Presence`: `hub.Count("board")` is "N watching", and a join or a leave renders the board again.
- `<details>` inside morphed regions need `data-preserve-attr="open"`.
